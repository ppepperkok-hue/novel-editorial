# 编辑部驱动模型：可行性评估与任务清单（2026-08-11）

定位：项目已从「流水线」转向「文学编辑部」。核心目标是拟人化——外部节拍负责
「开门」（开工/定时），编辑部内部由任务板、承诺、消息、关系、反馈共同驱动。
本文评估该驱动模型的可行性、性能成本，并列出分阶段任务。

## 一、可行性评估

| 机制 | 技术可行性 | 与现有架构兼容 | 主要风险 | 工作量 |
| --- | --- | --- | --- | --- |
| 消息总线 mailroom | 高（纯库函数+SQLite） | 高（`agent_tool_loop` 单点注入） | 低 | 小 |
| 记忆/关系/承诺数据层 | 高（幂等迁移机制现成） | 高 | 低 | 小 |
| 注入快照 | 高（`build_system` 是唯一组装点） | 高 | 注入膨胀 → 配置化截断 | 小 |
| outbox 解析落库 | 中高（LLM 输出 JSON，`robust_json` 容错） | 高 | 解析失败需显式留痕跳过 | 小 |
| 承诺机制 | 中高 | 高 | 自由文本承诺不可靠 → 走结构化字段（周记/会议 JSON 的 `promises` 数组） | 中 |
| 关系演化 | 高（事件钩子：打回/采纳/协作/兑现） | 高 | 数值封顶与衰减策略需测试 | 中 |
| 任务板升级 | 高（`agent_actions` 加列+认领接口，web_api 注册表现成） | 高 | 认领状态机（pending/claimed/in_progress/done） | 中 |
| 主编动态分派 | 中高 | 中（改动 `editorial_daily` 固定序列） | **最高**：分派失控风险 → 保留 `DISPATCH_MODE=fixed` 默认，editorial 灰度 | 大 |
| 审稿打回协商 | 中高（`_run_track` 回环 + 消息） | 中 | 重写循环成本与死循环 → 重试上限+熔断 | 中 |
| 自由会议 | 中（`meeting_session` 已有状态机） | 中 | 消息驱动对话状态复杂 → 分两期：先插话，后自由 | 大 |
| 编辑部视图 | 高（web_api 注册表 + 前端 NAV 现成） | 高 | 低 | 中 |

结论：**整体可行，无技术死路。** 高风险点只有主编动态分派与自由会议，二者都有
「保留固定模式 + 灰度开关」的安全路径。其余是数据层与注入层的机械扩展。

## 二、性能与成本评估

### 注入开销（每次 agent 调用）

| 快照 | 条数 | 截断 | 估算 token |
| --- | --- | --- | --- |
| 收件箱 | 8 | 每条 200 字 | ~900 |
| 最近记忆 | 3 | 每条 150 字 | ~250 |
| 关系快照 | 3 | 每条 80 字 | ~150 |
| 未兑现承诺 | 3 | 每条 100 字 | ~180 |
| 待办行动项 | 3 | 每条 100 字 | ~180 |
| 合计 | — | — | ~1.6K token/调用 |

### 日更成本增量（当前日更约 15 次 LLM 调用）

| 项目 | 估算 |
| --- | --- |
| 注入增量 | 15 次 × 1.6K ≈ 24K token/天；pro（planner/写手×2）约 8K×0.01 + flash 16K×0.002 ≈ 0.11 元/天，月约 3.3 元 |
| 主编分派（editorial 模式） | +1~2 次 pro/flash ≈ 0.01–0.02 元/天 |
| 打回协商（仅失败时） | 每章最多 1 轮重写 ≈ 极端 +4 次 flash ≈ 0.012 元/天（低概率） |
| 自由会议 | 周会 20–40 次 flash 增至 40–60 次 ≈ +0.04–0.08 元/周 |
| 合计 | 月增量约 3.5–4.5 元，占 100 元预算的 ~4% |

### 性能影响

- 注入使单次 prompt 增加 ~1.6K token，单次生成延迟增加数秒；对日更 20–60 分钟
  总时长无感。
- 消息/承诺/关系全部落 SQLite，零额外 LLM 调用；关系与承诺更新合并进现有周记
  调用（`memory_updates`/`relation_updates`/`promises` 字段），不新增调用次数。
- 预算熔断（`preflight.check_budget`）与重试上限兜底，成本不可失控。
- 建议：注入按 agent 过滤（写手/审稿/主编/记忆官需要协作快照，work_meta/guard
  可不注入），可再省约 40%。

## 三、任务清单

### 阶段 0 · 地基（P0，全部小步、每步全量回归 279+8）

| 任务 | 内容 | 依赖 | 验收 |
| --- | --- | --- | --- |
| T1 | 四张新表：`agent_messages`/`agent_relations`/`agent_memories`/`agent_promises`（幂等迁移+索引） | 无 | 迁移幂等；测试 |

| T4 | outbox：agent 输出 JSON 携带 `outbox`，解析落库、注入即标读、失败显式留痕 | T2/T3 | outbox 解析与标读测试 |
| T5 | web_api 只读接口（走路由注册表）：`/api/agents/mailbox|relations|memories|promises`；control action `process_messages` | T2 | 接口测试 |

### 阶段 1 · 内驱（P1，承诺/关系/任务板）

## 四、结论与推进建议

- 可行性：全部机制可落地，无死路；风险集中在 T10/T13，均有固定模式兜底。
- 成本：月增量约 3.5–4.5 元（预算 100 元），注入按 agent 过滤后更低；延迟无感。
- 推进：先做阶段 0（T1–T5），每步全量回归；阶段 1 的 T6/T7/T8 可与 T3 并行设计；
  阶段 2/3 在阶段 0/1 稳定后灰度。
