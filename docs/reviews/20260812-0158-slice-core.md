Baseline: python -m compileall -q novel_editorial passes (exit 0), all 33 modules in the slice import cleanly under the project venv, and the ~20 tools/* interfaces referenced by the slice (agent_meeting, workday, editorial_daily, mailroom, preflight, novel_knowledge, render_workflow, etc.) match the call signatures used. One P1, one P2 and three P3 issues were found. The P1 (control.py background workers hardcoding config.DB_PATH while the panel/desktop app runs on a different --db database) silently breaks the core 开工/日更/周会 loop in the packaged desktop artifact, so the slice is not correct as-is; the P2 reminder miss (~97% of days) is a silent user-facing failure.

Full review comments:

- [P1] Scheduler control hardcodes ROOT/demo.db, diverging from the panel's --db target — E:\code\novel-editorial\novel_editorial\services\control.py:108-119
  All background execution paths in novel_editorial/services/control.py connect to `config.DB_PATH` (ROOT/demo.db) instead of the database the panel was started with: `_background_daily` (control.py:111,119), `_background_workday` (132,142), `_background_close` (155,160), `_background_resume` (173,178) and `_weekly_worker` CLI invocations (214,217,219); `scripts/install_daily_task.ps1:28` also resolves the task DB to ROOT/demo.db. But the panel serves whatever `--db` was passed to `make_handler` (web_api.py:130), and the packaged Electron app launches `pythonw -m novel_editorial.web_api --db %APPDATA%\<app>\demo.db` (desktop/main.js:51-60). In a packaged install (or any non-default `--db` override) clicking 开工/日更/周会/收工/继续 runs against a stale/empty ROOT copy, `manual_run_requested` is written to the panel DB but read by the run from the other DB, and the panel never reflects the run — a silent divergence with no error surfaced. Thread `db_path` through `handle_control`/the `_background_*` workers (and into install_daily_task.ps1) instead of using the module constant.

- [P2] Reminder daemon polls every 30 min but only fires on an exact-minute match — E:\code\novel-editorial\novel_editorial\services\reminders.py:126-143
  novel_editorial/services/reminders.py:126-143 sleeps `interval_seconds` (1800) between polls and fires only when `now.hour == int(rt[0]) and now.minute == int(rt[1])` — an exact-minute equality check whose phase depends on when the server process started. Poll instants occur at (start+60) mod 1800 seconds, so the 20:00 reminder fires only when that phase falls in the 60-second target minute (1/30 ≈ 3.3% of start times). Simulation over all 1440 minute-of-day start times confirmed 1400 misses (97.2%): the scheduled desktop reminder silently never fires on almost every day. The check should compare against a stored last-check timestamp (fire when the target time has passed since the previous poll) or sleep until the target minute.

- [P3] /api/knowledge_drafts distill branch leaks a SQLite connection per request — E:\code\novel-editorial\novel_editorial\web_api.py:920-929
  web_api.py:920-929: the `distill` action closes the request connection, runs `distill_lessons.distill_latest`, then reopens `conn = db.connect(db_path)` but nothing closes that new connection before `self._json(result)` (do_POST has no finally; the except handlers only close on error). Each distill call leaks one open sqlite3 connection (WAL file handle held until GC). Close the reopened connection after `_json` or restructure with try/finally.

- [P3] hot_topics.json written non-atomically and read without error handling — E:\code\novel-editorial\novel_editorial\hot_topics.py:285-288
  hot_topics.py:285-288 persists via `Path(out_path).write_text(...)` with no temp-file/rename, while misc.load_hot_topics (misc.py:36-41) does an unguarded `json.loads(...)`. A refresh interrupted mid-write (Ctrl+C, crash, disk full) leaves a truncated file that makes `/api/hot_topics` and `/api/dashboard` (which calls `load_hot_topics` via build_payload) return 500 until the next successful refresh. Wrap the read in try/except returning `{"present": False}` and write via a temp file + `os.replace`.

- [P3] CLI entry points default --db to relative 'demo.db', silently using a different database outside ROOT — E:\code\novel-editorial\novel_editorial\scheduler.py:101-104
  scheduler.py:101/104, monitor.py:71/75, seed_demo.py:61/66 (and the same pattern in novel_flow.py, autopilot.py, web_api.py) default `--db` to relative `demo.db` and pass it straight to `db.connect`, which creates the file if missing. Run from any other working directory (scheduled task without WorkingDirectory, scripts dir, IDE launcher) these tools silently create and operate on a fresh empty DB instead of ROOT/demo.db. Default to `str(config.DB_PATH)` or resolve relative paths against ROOT before connecting.
