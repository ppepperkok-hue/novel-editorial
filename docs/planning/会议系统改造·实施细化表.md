# 会议系统改造：实施细化表（hermes 模式 · 栈内子集）

承接《会议系统改造·hermes模式评估与工程表.md》。本文件把工程表细化为可执行步骤，并固化每步审查机制。**效果预期以第 3 节验收场景为准，每一步对照验收，不靠感觉。**

## 1. 效果预期声明

改造完成后，以下场景必须真实可跑（dry-run 与真实各一次）：

1. 发起「自由讨论」会议（如「讨论下一卷剧情」），**无人 @、无人点名**：文策先抛方向，守正主动质疑逻辑漏洞，墨白补细节，阿读从读者视角插话——形成自然接龙，界面实时滚动，能看到「墨白正在思考…」状态。
2. 老板插话 `@守正 说说你的顾虑`：守正必答；未 @ 的相关编辑视话题可继续接，不相关的不必开口。
3. 讨论跑题（聊到封面）：主席像真人主编一样主动插话拉回主题；冷场约 30 秒时，有编辑主动发起新话题或主席推进。
4. 会议中编辑请求拍板（如采纳经验卡草案），面板弹出审批卡，老板选择同意/拒绝/暂缓，编辑收到结果后继续。
5. 老板说「总结一下」：主席当场输出报告，行动项落盘，会议可结束或继续。
6. 长会议（50+ 轮）上下文不爆：自动压缩后关键决策与待办仍保留；固定轮次周会零回归；刷新/断网后状态恢复、消息不丢不重。

**达标前提（写进代码评审清单）**：执行器桥必须注入人格档案、该编辑本周日记/心情、会议材料与历史，输出保持六段结构；桥浅了不算完成。

## 2. 审查机制（每步强制）

### 2.1 步级审查（每完成一个垂直切片）
- 切片 ≤100 行；写完 → 跑定向测试 → 主 agent 五轴自审（正确性/边界/错误处理/集成/安全）→ 提交（本地分支，不推送）。
- 自审对照：反模式族（裸 JSON 解析/吞错/假绿灯/硬编码/类型守卫/死代码）、四态（加载/空/错误/成功）、量化硬限制（文件 ≤500 行、函数 ≤120、嵌套 ≤3）。

### 2.2 阶段审查（每完成一个阶段）
- 跑 `powershell -ExecutionPolicy Bypass -File scripts/run_review.ps1 -Scope uncommitted` 独立审查；P0/P1 必须清零，P2 登记到 `docs/reviews/` 临时报告。
- 全量回归：后端 `python run_tests.py`、前端 `cd webapp && npm test && npm run build`。
- 向老板汇报四要素：在干什么、影响什么、验证了什么、下一步。

### 2.3 收尾分片审查（阶段 7 完成后）
- `scripts/run_review.ps1 -Scope slices` 分片全库审查（editorial / core / knowledge / frontend / platform / tests 六片，并行 CLI）。
- 汇总 → 核实层（confirmed / false_positive）→ 修复（先写失败测试）→ 回归检查层 → 轮次归档 `docs/reviews/rounds/`。

### 2.4 测试纪律
- 测试一律临时库 + mock LLM + 不触真实 n8n/番茄/webhook；修 bug 先写失败测试。
- SSE 相关测试用 test-setup 的 MockEventSource；@路由用纯函数单测（中文边界用例）。

## 3. 分步实施（每步含验收与审查）

### 阶段 0 · 数据层（评估文档阶段 0）

**步骤 0.1 迁移与表结构**
- 内容：`db.py` 幂等新增 `meeting_messages`（id/session_id/seq/from_agent/role/kind/body/mentions JSON/status/created_at）与 `pending_interactions`（id/session_id/agent/kind(approval|clarify)/payload JSON/status/created_at/expires_at/resolved_at/resolution）；`meeting_sessions` 增加 `mode` 列（默认 `rounds`）。
- 验收：迁移重复执行不报错；PRAGMA 表结构断言通过。
- 测试：迁移幂等测试（连续两次建表/加列）；现有 511 后端测试全绿。
- 审查：步级自审 + 阶段审查（F10 注入类：SQL 全部参数化）。

### 阶段 1 · @提及路由与执行器桥

**步骤 1.1 @提及解析器**
- 内容：新建 `tools/meeting_mentions.py`，参考 hermes mention-routing 移植：`find_mentions(content, names)`（中文标点边界、@all、去 token、结构化 mentions JSON）。
- 验收：单测覆盖：`@守正`、`@all`、`@守正，回应墨白`、邮箱/URL 不误判、名字含特殊字符。
- 审查：纯函数单测即验收；阶段审查扫描无裸解析。

**步骤 1.2 执行器桥 `meeting_executor.py`**
- 内容：`reply_to_mention(conn, session_id, agent, mention_msg)`：组装上下文（会议材料 + 历史截断 + 该编辑本周日记/心情 + 被 @ 内容）→ 调 `agent_meeting.ask`（保持六段结构）→ 写 `meeting_messages` → 返回消息 id；失败显式留痕（audit_logs + status=failed）。
- 验收：dry-run 下 @单人/@多人/@all 均正确落库；输出含六段字段；LLM 异常时消息表有 failed 记录且不中断会话。
- 审查：反模式族 F1/F3/F7 扫描；阶段审查。

### 阶段 2 · free 模式：自主发言调度器（核心，重写）

**设计原则**：事件驱动 + 自主接话 + 沉默权 + 主动议题 + 主席调停。不依赖 @/点名才发言。

**步骤 2.1 事件总线与会话模型**
- 内容：`meeting_session.py` 支持 `mode=free`；新增事件类型：`user_message`（老板插话/@/指令）、`agent_message`（编辑发言）、`approval_resolved`（审批结果）、`cold_timer`（冷场）；`get_session` 返回 messages（从表读）+ 当前 thinking 名单 + 队列状态；session 级锁。
- 验收：rounds 模式零改动；free 会话可创建/推进/取消；事件按序处理。

**步骤 2.2 接话决策器 `meeting_speaker.py`**
- 内容：每个触发事件产出「候选名单」：被 @ 的 agent 必答；其余按「话题关键词 ∩ 该 agent 关注点/人格档案」相关性打分，取 top K（K 可配置，默认 2）；排除正在发言/冷却中的 agent。
- 验收：@守正 时守正在必答名单；未 @ 时仅相关 agent 进候选；每事件候选 ≤ K+@数。
- 测试：相关性打分单测（关注点匹配/性格权重）；上限断言。

**步骤 2.3 并行发言池与沉默权**
- 内容：候选 agent 并行调用（每 agent 一次 LLM，输入 = 讨论历史 + 该编辑本周日记/心情/关注点 + 事件消息；输出允许 `{speak:false}` 或六段结构）；实际发言落 `meeting_messages` 并广播；同 agent 不并发 + 两次发言最小间隔（默认 60s）防刷屏；无人发言则进入冷场计时。
- 验收：dry-run 下未 @ 也有 agent 自然接话；允许全部沉默；同 agent 不并发；间隔生效。
- 测试：并行/间隔/沉默权测试；rounds 回归。
- 审查：锁与并发专项（F7/F9）；反模式族 F3/F4（沉默不吞错，落 `no_speech` 事件）。

**步骤 2.4 冷场与主动议题**
- 内容：冷场计时器（默认 30s）：先触发「待议议题」注册表（编辑周记/日记中的 concern 可登记为议题，冷场时优先抛给对应编辑），无议题则触发主席推进；主席自由模式角色 = 拉回跑题、冷场推进、用户喊「总结」时输出报告并落盘行动项。
- 验收：冷场 30s 内必有动作（议题发言或主席发言）；跑题时主席可拉回；「总结一下」产出报告 + 行动项。
- 测试：冷场计时（mock 时钟）、议题注册触发、主席总结落盘。

**步骤 2.5 防失控保险丝**
- 内容：每事件接话上限（默认 2+@数）、全局消息速率上限、同 agent 间隔、冷场检测（无死循环）；全部参数进 settings 可调。
- 验收：50 条事件模拟下消息量有界；参数可调。
- 审查：阶段审查 + 模拟压测。

### 阶段 3 · 审批/澄清路由（依赖事件总线）

**步骤 3.1 交互事件 API**
- 内容：`web_api.py` 新增 `POST /api/meetings/interactions/respond`（幂等：已响应返回 stale）；`meeting_session` 提供 `request_interaction` / `resolve_interaction` / `expire_interactions`；过期清理随会话心跳执行。
- 验收：请求→响应→过期全路径；重复响应第二次返回 stale 且不改变结果。
- 测试：幂等/过期/越权（非本会话）测试。

**步骤 3.2 事件入 SSE（依赖阶段 4，先留接口）**
- 内容：定义事件负载契约 `{type:"approval", interaction:{...}}`；本步只落库不推送，接口留 `broadcast_hook`。
- 验收：契约字段与前端审批卡一致（id/agent/question/choices/expires_at）。

### 阶段 4 · SSE 实时推送

**步骤 4.1 会议事件流端点**
- 内容：`web_api.py` 新增 `/api/meetings/events?session_id=`（独立线程订阅表，复用 `_sse` 模式）：事件 `message/status/approval/heartbeat`；无事件时 15s 心跳。
- 验收：双客户端同收事件；推送期间 `/api/control` 仍可响应（非阻塞验证）；断开后客户端重连可拉全量消息补齐。
- 测试：SSE mock（MockEventSource）；连接数上限与清理测试。
- 审查：并发/线程安全专项（订阅表锁、连接清理）。

### 阶段 5 · 前端聊天室重构

**步骤 5.1 会议中心房间视图骨架**
- 内容：MeetingsPage 重构为房间形态：左侧会话信息（参会者/模式/状态）+ 主消息流（虚拟列表 + 增量渲染）+ 底部输入区（文本 + @插入下拉 + 发送）。
- 验收：消息流从轮询切到 EventSource；增量追加不整页重渲染；空态/加载/错误四态完整。

**步骤 5.2 @插入与审批弹窗**
- 内容：输入框 `@` 弹出参会编辑列表（头像+名字），选择后插入 `@名字`；审批事件到达弹出审批卡（同意/拒绝/暂缓 + 过期倒计时）。
- 验收：@插入交互测试；审批弹窗出现/响应/消失闭环；motion 动画低强度。

**步骤 5.3 模式切换与状态轨道**
- 内容：发起会议时选择 rounds/free；free 直播头部显示当前思考中的编辑（头像脉冲）+ 队列长度；保留推进/结束/取消按钮。
- 验收：两种模式 UI 均可用；视觉截图对比概念稿。
- 审查：前端分片审查；impeccable detect 清零。

### 阶段 6 · 上下文压缩增强

**步骤 6.1 token 预算与尾截断**
- 内容：free 模式按配置阈值（如 120k 字符）触发压缩：历史截断为摘要锚点 + 最近 N 条；`meeting_messages` 标记 `compressed_at`。
- 验收：500+ 消息模拟会议不超预算；压缩后关键决策/待办仍可检索。

**步骤 6.2 压缩事件与恢复**
- 内容：压缩动作广播 `status:compressing`；断线重连拉取时含摘要锚点，不重复压缩。
- 测试：长会议模拟；压缩幂等（重复触发不二次压缩）。

### 阶段 7 · 全量回归与真实验证

- 内容：dry-run 端到端（mock LLM + 临时库）跑通全场景；真实会议一次（可选，需用户在场）；`run_review.ps1 -Scope slices` 分片审查 + 修复闭环。
- 验收：后端全量测试绿、前端 40+ 测试绿、build 绿；P0/P1 清零；效果预期 6 场景逐条打勾。

### 阶段 8 · 文档与部署

- 内容：README 会议章节、backlog 更新、审查报告归档 `docs/reviews/rounds/`；提交推送（待用户确认后收尾，不写敏感信息）。

## 4. 老板汇报节奏

- 每完成一步：一句话说明做了什么、验证了什么。
- 每完成一阶段：四要素汇报（在干什么/影响什么/验证了什么/下一步）+ 效果预期场景打勾进度。
- 阶段 7 真实会议前：与用户约定时间，演示 6 场景中的关键 4 个（自由讨论/@指定/审批/恢复）。

## 5. 假设与默认

- `mode` 默认 `rounds`；free 为增量能力，可开关。
- 转交链（handoff）不在本工程表，free 稳定后另行评估。
- hermes 代码仅参考，`mention-routing` 移植时在文件头标注来源与许可。
- 所有改动在 `codex/frontend-redesign` 分支（会议改造如涉后端，可开子分支或同分支，收尾时一并合并）。
