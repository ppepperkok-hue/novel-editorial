The webapp slice is in good shape (tests and build pass, API contracts match), but the desktop slice ships two P1 regressions: the release script uploads an installer name that latest.yml does not point to (auto-update 404s), and moving demo.db into the installer resources makes every upgrade overwrite the user's runtime database. These need fixes before release.

Full review comments:

- [P1] release.js uploads ASCII exe whose name differs from latest.yml path, breaking auto-update — E:\code\novel-editorial\desktop\release.js:44-46
  electron-builder generates `latest.yml` with the GitHub-safe installer name derived from package.json `name` (`novel-pipeline-desktop-setup-1.0.0.exe`, verified in desktop/release/latest.yml; NsisTarget.js `generateGitHubInstallerName` is used because the Chinese productName is non-ASCII). release.js:44 copies the installer to `novel-editorial-desktop-setup-${version}.exe` (renamed in c41f8ff) and uploads only that copy plus latest.yml (release.js:79-81). The GitHub release therefore never contains the file `latest.yml` points to, so electron-updater's download of `path` returns 404 and in-app auto-update always fails on every release.

- [P1] demo.db moved into resources dir; NSIS upgrade overwrites it and wipes user run data — E:\code\novel-editorial\desktop\main.js:52-55
  ensureApi now uses `path.join(ROOT, "demo.db")` (desktop/main.js:55), i.e. `resources/novel-pipeline/demo.db` in packaged builds, and package.json extraResources bundles demo.db into every installer (desktop/package.json:42). The previous build kept the DB in `app.getPath("userData")` (see git diff of this commit), which survives upgrades; NSIS upgrades overwrite resources files, so installing a new version replaces the user's live DB (daily_runs, publish_logs, audit, meetings, agent_diaries, chapters) with the seed DB from the build machine. With a perMachine install the resources directory is also read-only for standard users, making the DB unwritable at runtime. The cross-drive relpath error that motivated this change should be fixed in control.py instead of relocating the DB.

- [P2] ensureApi failure leaves the app running with no window and no tray — E:\code\novel-editorial\desktop\main.js:241-249
  When the API does not become ready within 20s (missing pythonw, port 8000 occupied, or slow cold start), `ensureApi` throws and the whenReady catch only shows an error box and returns (desktop/main.js:241-249). The app is not quit and no window/tray was created, so after dismissing the dialog the process lingers headlessly; the user cannot retry or exit from the UI, and a second launch only triggers `second-instance` -> `showWindow`, which may create a blank window if the API never came up.

- [P3] watchExecutions only tracks list[0], so terminal notifications can be missed — E:\code\novel-editorial\desktop\main.js:196-209
  The 30s poll compares only `list[0]`'s key (desktop/main.js:196-209). If an execution finishes and a new run takes the top slot between two polls, or two executions complete within one interval, the finished run's success/failure notification is silently dropped; the app also never notifies for the first terminal state after startup because `lastExecKey` starts empty. The notification is advisory, but the logic provably skips terminal outcomes.

- [P3] refresh() resets refreshing flag before the fetch completes — E:\code\novel-editorial\webapp\src\App.jsx:62-65
  In App.jsx:62-65 the async `refresh` calls `setRefreshing(true)`, then `refreshDashboard()` (which only bumps a tick counter synchronously), then `setRefreshing(false)` immediately, so the refresh button's spinner/disabled state never actually shows and the function's `async`/await is a no-op. The refresh itself still works via the polling effect; this only breaks the loading indicator.
