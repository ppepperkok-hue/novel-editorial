# 04 可执行单元（Executable Units）

功能拆成可独立验收的单元，形成 backlog。估算依据：复杂度、依赖、验证成本。

## 里程碑与自然行为限度

| 里程碑 | 范围 | 自然行为限度 |
| --- | --- | --- |
| M1 最小可验证版本 | 一轮“带着自然行为”的协作闭环：老板下令 → 编辑部讨论 → 写手产出样章 → 质量门 → 老板拍板；全程有日志，多作品隔离 | 最小限度：只埋自然行为种子（角色自主发起话题、主动退稿、反驳），其余环节仍偏结构化。**状态：完成（2026-08-13，tag m1-complete）** |
| M2 伙伴完整与信息分层深化 | 完整档案、立场与拒绝、私有记忆、分层视图与按需检索、叙事追踪、质量门完善 | 放宽：行为更多由角色内在驱动（立场、记忆、情绪状态），角色更“有自己” |
| M3 开源与可见性 | 快速开始、文档、可见性基础形态（事件流 / 穿透查询 / 拍板提醒） | 继续放宽：可见性下角色可自主推进更多环节，作者更少驱动 |
| 后置 | 图形面板（三扇窗完整呈现）、外部集成 | 方向：自然为主、结构为辅 |

原则：放宽以不破坏分层骨架、不失控为前提；每个阶段都有可验收的自然行为用例，放宽多少、验收多少。

## 排序依据

- 依赖优先：U1–U5 打地基，再上协作与记忆。注意：编号不是实现顺序，实现顺序以“依赖”列为准（如 U7 依赖 U12，U12 应先于 U7 落地）。
- 风险前置：U5（LLM 客户端）与 U13（质量门）是技术风险最高的两块，提前啃；U15 端到端演示保证整体可验证。
- 价值优先：M1 先兑现“分层编辑部真实且自然地运作”的最小闭环，不做全量功能。

## 反盲从三问

1. 这是需求还是方案？“能对话、能产出草稿、能检测 AI 味”是需求；“用 CLI 命令实现”“注入记忆包”是方案。
2. 依据是什么？每个单元都能回溯到功能（F1–F21）与目标（G1–G5）；拆不动的功能已回上层重新定义。
3. 不做会怎样？M1 之外的功能只是延后，不是砍掉；没有 M1 闭环，后面都是空中楼阁。
