# Agent 自由度改造 · 评估与工程表（2026-08-11）

定位：项目已从「流水线」转向「文学编辑部」。核心目标是拟人化——agent 从「被允许说什么」走向「被允许做什么」：分派真正生效、认领真正兑现、表达有出口、提议有闭环。本文评估该改造的技术可行性、成本与架构影响，并列出分阶段工程表。所有数字以当前代码为准（371 后端 + 15 前端测试）。

## 一、现状评估：自由度矩阵与名实差距

详细九维评估见 `agent自由度评估.md`。结论摘要：

| 维度 | 得分 | 一句话 |
| --- | --- | --- |
| 触发 | ★ | 何时工作完全由调度器决定，无自主启动 |
| 任务 | ★★ | 任务板可认领，但不影响主流程 |
| 流程 | ★★ | 审稿可打回，但分派灰度默认关闭 |
| 表达 | ★★★ | 人格丰富，日常输出被 JSON 模板锁死 |
| 工具 | ★★★★ | function calling 自主检索知识，最像人 |
| 记忆 | ★★★ | 多级记忆注入，但模型用不用不可控 |
| 关系 | ★★ | trust/friction 只是提示词文本，不改决策 |
| 主动性 | ★★ | 能发消息投议题，不能自主行动 |
| 硬约束 | 护栏 | 质量门/合规/预算不可绕过，合理 |

名实差距核心：主编分派（editorial）代码已存在但默认 `fixed` 未生效；任务认领只改状态不改行为；消息无「响应→重做」回路；议题提议无「提议→行动项→兑现」闭环。**自由度是「被允许说什么」，还不是「被允许做什么」。**

## 二、技术可行性评估

| 改造 | 技术可行性 | 与现有架构兼容 | 主要风险 | 工作量 |
| --- | --- | --- | --- | --- |
| F1 主编分派生效 | 高（`_dispatch` 已实现分派与广播，只差注入写手 prompt） | 高（`_writer_task` 是轨道 prompt 唯一组装点） | **中**：eic 分派输出不稳定 → 已有 degraded 降级回 fixed；注入仅为追加文本不改流程 | 小 |
| F2 认领兑现 | 高（只读 `agent_actions`，SQLite 查询） | 高（写手 prompt 组装点现成） | 低：认领任务语义与今日章节不匹配 → 只注入提示文本，不强制 | 小 |
| F3 表达出口 | 中高（`quality_reports` 需幂等加 notes 列，`db._migrate` 机制现成） | 高（审稿 JSON 解析点集中在 `_run_track`/`quality_gate`） | 低：notes 缺失/非字符串 → 默认空串，不影响 JSON 兼容 | 小-中 |
| F4 议题闭环 | 高（`agent_messages(topic_request)` 与 `activity.create_action` 均现成） | 高（会议收尾已有动作序列） | 低：重复转换 → 以 mail archived + session 幂等防重 | 小 |

结论：**整体可行，无技术死路。** 四刀都是数据层/提示词层的机械扩展，最大风险仍是 F1 的分派输出质量，而它已有「保留 fixed + 降级」的安全路径。

## 六、验证纪律

- 每步跑 `python run_tests.py`（全量）；前端改动跑 `cd webapp && npm test && npm run build`；测试一律临时库 + mock LLM。
- 修 bug 先写失败测试；每步提交推送，工作树不堆积。
- 全部完成后产出 `docs/reviews/YYYYMMDD-freedom-upgrade-review.md`（P0–P3 + 影响评估表），更新 README/evolution。

## 七、需要老板拍板的决策点

1. `DISPATCH_MODE` 默认值：历史安全路径是默认 `fixed`、editorial 灰度；本次建议**默认 `editorial`**（env 可回退），让分派真正生效。是否认可？
2. F3 的 notes 展示位置：建议在章节详情页质量卡片展示（空则隐藏），是否认可？
3. 四刀节奏：F1→F4 每刀完成后向您汇报并提交，还是四刀一次做完再汇报？建议每刀一汇报。
