## 第 1 层：核心价值（01a）

### 一句话价值主张

为独自管理作品、又不爱天天敲命令行的作者，解决「编辑部的工作藏在 CLI 和数据库里」的问题，带来「打开网页就能写、聊、看、查、拍板，编辑部全程可见可管」的结果。

### 核心用户与核心场景

- 作者本人（主）：打开界面 → 跨作品看动静 → 进作品跟伙伴对话 → 写 / 改正文 → 看审稿意见与质量门 → 就地拍板；讨论、动机、耐心、行为时间线一屏可查。
- 开源外部作者（次）：干净环境一条命令起服务，无 key 也能打开示例编辑部，30 分钟跑通一轮「建作品 → 对话 → 写作 → 拍板」。

### 价值边界（明确不解决）

- 不解决多用户鉴权与云端服务：本地单机、localhost 单用户，开源者自担部署。
- 不解决移动端 App 与多人实时共编：桌面浏览器 / 桌面应用优先。
- 不解决自动发布与第三方平台对接：发布不在本项目边界（沿用 06 明确不做）。

### 反盲从三问

1. 需求还是方案？「作者要一个功能齐全的界面来完成创作与协作」是需求；React/Vite/SSE、界面布局都是方案，还原成问题是「CLI 之外要有一扇完整的窗户」。
2. 依据是什么？G1（老板可穿透、关键处拍板）、F17–F19（可见性机制）与用户明确拍板的「广义前端、功能齐全」；CLI 已交付能力是界面必须覆盖的地图。
3. 不做会怎样？作者只能敲 CLI，新用户上手成本高，老板视角不完整；核心创作不受影响，但产品形态残缺、开源吸引力打折。

### 做 / 不做

**做**：FE-F1～FE-F11 全功能界面；面板 MVP 迁移并入（FE-G4）；API 写面扩展（对话 / 草稿 / 结构 / 设定知识 / 讨论 / 风格 / 模板 / 导入导出，逐一按 CLI 命令映射）；正文在线编辑（手动打字 + LLM 生成 / 修订并存，先纯文本 + Markdown 预览，富文本后置）；事件流实时推送（SSE，断线重连，轮询仅作降级）；Electron 桌面壳（web 同源打包，Windows 优先、macOS / Linux 尽力而为）。

**不做**：多用户鉴权与云端服务、移动端 App、多人实时共编、自动发布与平台对接、富文本编辑器（先纯文本 + Markdown 预览，富文本后置）。

### 依赖与实施顺序

API 契约扩展（FE-F11）→ 作品 / 对话 / 写作 / 拍板主链路（FE-F1～F4）→ 结构 / 设定知识 / 总览与事件流（FE-F5/F6/F9）→ 质量风格（FE-F8）→ 自由意志可视化（FE-F7）→ 数据管理（FE-F10）→ 设计打磨与 QA。

## 全局约束与风险

- 约束：同仓库独立大项目；本地单机、个人 + 开源；前端只消费 API、不复制业务逻辑；后端写面变更遵守 docs/architecture/extension.md 与依赖方向（api → core）；不破坏既有 CLI / API 契约（测试守卫）；前端四命令（lint / typecheck / test / build）是每次验收的硬门。
- 风险 1：范围过大 → 四个里程碑分期交付，每期独立验收，不做大爆炸式一次写完。
- 风险 2：API 写面扩展破坏只读优先纪律 → 写操作收敛为 CLI 命令逐条映射，契约测试 + 对照测试双保险。
- 风险 3：CLI 与界面双通道结果漂移 → 数据同源红线 + 对照测试（同一数据双通道断言）。
- 风险 4：实时推送断线 / 积压 → SSE 断线重连 + 游标续传，轮询保留为可配置降级，不静默丢事件。
- 风险 5：编辑器体验（手动写作 vs LLM 生成）边界不清 → 立项阶段明确并存模式与保存 / 版本语义后再动工。
- 风险 6：Electron 打包的平台差异与体积 → 版本锁定、构建命令显式化；Windows 优先，macOS / Linux 尽力而为并写清限制。
- 决策记录：同仓库独立大项目（用户拍板）；广义全功能前端（用户拍板）；面板 MVP 并入作起点；事件流用实时推送、不做轮询主路径（用户拍板）；正文编辑器按「手动 + LLM 并存、纯文本 + Markdown 预览」立项（用户拍板）；边界扩宽纳入 Electron 桌面端（用户拍板）；发布 / 鉴权 / 移动端沿 06 明确不做。
