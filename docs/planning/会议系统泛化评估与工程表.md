# 会议系统泛化评估与工程表（Meeting System Generalization）

## 一、现状盘点：已经泛化 vs 仍绑死周会

会议系统实际上已经是一个「可交互、可插话、可记忆」的通用会议引擎，但概念与实现仍有一半绑在「周会」上。逐层盘点如下。

| 层次 | 已经泛化的部分 | 仍绑死周会的部分 |
| --- | --- | --- |
| 数据层 | `meeting_sessions.kind` 字段存在（默认 'topic'）；`weekly_meetings.kind` 存在（'weekly'/'topic'）；前端档案已按 kind 显示「周会/专题会议」 | 表名 `weekly_meetings` 历史遗留；`meeting_sessions` 创建时硬编码 kind='topic'，`create_session` 不接受 kind 参数 |
| 会议引擎 | `chair_pick` / `round_speech` / `chair_summary` / `compress_history` 全部与具体会议内容解耦；支持任意主题、`novel_id=0` 新书选题会、轮次间插话、`MEETING_MODE=open` 自由对话、议题提议采集（topic_request） | 模块 docstring 仍是 "weekly meeting engine"；`round_speech` JSON 字段硬编码 `weekly_summary`，提示词写「这是周会」「请先做本周小结」；六段发言结构（本周小结→感受→意见→顾虑→提案→优先级）对所有会议强制 |
| 材料层 | `build_planning_materials` 已支持新书选题会（无书时） | `architect_weekly.py` 模块名与 docstring 周会化；`build_materials` 的 agent_briefs 全是「本周」语义；材料固定一套（8 章摘要+热点+角色+质量+成本），不按 kind 裁剪；`weekly_chapters` 用 `novels.updated_at` 近似当周起点，本身不严谨 |
| 会后动作 | `apply_report`（蓝图/卷目标/封面）与 `create_planning_from_next_book`（新书）已按有无书分流；post-meeting actions 已接入 | 动作路由只有「有书→apply_report」「无书→建 planning 书」两条，没有按 kind 走不同产出（事故复盘没有整改动作、学习会没有知识草稿、完结评审没有完结决策） |
| 触发层 | 手动开会已独立于周会定时；`control.py` 已有 `run_weekly` / `run_knowledge_keeper` action | `weekly.lock` 锁文件、`run_weekly` 命名周会化；没有事件驱动入口（日更失败自动复盘会、质量下滑自动评审会等） |
| 前端 | MeetingLive 已支持主题输入、轮次插话、会议直播；MeetingsPage 已区分专题/周会 | 创建会议没有 kind 选择与议程模板说明；直播页文案「与周会共用引擎」；档案页只能按 kind 简单过滤，看不到会后产出 |
| 留痕 | audit 已记录 start/completed/failed/timeout/post_meeting_actions；会议记忆写入 `agent_diaries(diary_type='meeting')` | 报告无材料清单/产出清单字段；各 kind 的留痕粒度相同，无法区分「这是一次事故复盘」 |

## 二、结论

会议引擎本身已经通用且稳定，缺口在「会议种类（kind）」没有成为一等公民：

1. **创建会议时无法选择会议类型**，所有会都叫专题会；
2. **材料、发言模板、会后动作三件事都不按类型变化**，所以周会能力没法迁移到事故复盘、学习分享、完结评审这些场景；
3. **命名与概念仍周会化**，影响后续扩展与前端表达。

更深一层：本项目的核心不是「跑通流程」，而是**模拟一个真实文学编辑部，让产出的小说有编辑部共识的沉淀、有拉锯的痕迹、有连续性，从而避免被读出 AI 味**。会议系统泛化正是把「周会」升级为「编辑部生活」的抓手——会议只是显影点，会前积累、会中拉扯、会后沉淀才是正文。

## 三、目标形态：会议类型（kind）一览

| kind | 编辑部对应 | 用途 | 材料侧重 | 发言结构（JSON 字段兼容） | 会后动作 |
| --- | --- | --- | --- | --- | --- |
| `weekly` | 编辑部例会 | 周例会（原周会，行为不变）：对齐目标、排下周班 | 周简报、本周数据、热点、行动项、角色状态、质量 | 本周小结→感受→意见→顾虑→提案→优先级 | apply_report + post-meeting actions |
| `topic` | 剧情碰头会 | 专题/剧情会（现状）：讨论当前剧情如何发展 | 全书上下文、最近摘要、伏笔、角色、知识库 | 主题观察→感受→意见→顾虑→提案→优先级 | apply_report + actions |
| `planning` | 选题会 | 新书选题会（现状）：讨论写什么书 | 热点、市场、读者、竞品、写作知识 | 市场观察→目标读者→差异化→风险→提案 | create_planning_from_next_book |
| `critique` | 单章会诊 | 针对一章/一稿的详细会诊：打回拉锯升级到会上 | 章节原文、质量报告、读者数据、伏笔台账、黑名单 | 这章好在哪→问题→动机/真实性→修改方案→优先级 | 打回/通过结论 + 修改指令注入下一稿 |
| `retro` | 数据复盘会 | 把完读率、追读、评论翻译成具体写作问题 | 读者数据、章节数据、评论、弃书点、质量趋势 | 数据告诉我什么→读者在哪弃→写作根因→改进→行动项 | 经验草稿 + 写作指令更新 |
| `review` | 收尾会 | 完结/作品评审：故事讲完没有、伏笔清完没有 | 完结指标、伏笔回收、角色弧、读者数据 | 完成度评估→问题→收尾方案→风险→提案 | 完结/继续建议 + 新书孵化（挂接 ending_judge） |
| `incident` | 危机处理会 | 事故复盘：日更失败、发布事故、设定冲突爆发 | 失败运行记录、质量报告、audit、相关章节 | 发生了什么→根因→责任/过程→改进→行动项 | 整改行动项 + 经验草稿（distill_lessons） |
| `learning` | 知识分享会 | 知识蒸馏：把经验/资料沉淀为知识包 | 知识包、知识草稿、热点、外部资料 | 我学到了什么→可用场景→与现状差距→提议→优先级 | knowledge_drafts 采纳/更新建议 |
| `free` | 茶水间闲聊 | 自由讨论：无议程，议题由 agent 平时投递的议题池驱动 | 由主席按讨论热度现场选；议题池（topic_request） | 自然发言，弱结构化，主席点名接话 | 仅行动项 + 记忆 + 灵感入点子池 |

## 三点五、从「开会」到「编辑部生活模拟」

只把会议类型做成一等公民还不够。真实编辑部里，会议之所以影响作品，是因为会前有积累、会中有拉扯、会后有沉淀，会议只是整条链路的显影点。这套模拟要成立，必须补上三个编辑部核心机制：

| 机制 | 编辑部里是什么 | 系统里对应什么 | 对「去 AI 味」的作用 |
| --- | --- | --- | --- |
| 拉锯（tension） | 作者想写爽、编辑要质量、读者要好看，三方拉扯 | 写手 vs 守正/润色 vs 阿读；打回重写、会诊会、意见分歧 | AI 味来自「无人反对」的顺滑；真实的拉扯会磨掉空话、逼出具体修改 |
| 共识（consensus） | 编辑部定期对齐「这本书到底是什么味道」 | 会议结论 →「编辑部共识/写作指令」→ 注入下一章 writing_context | 前后章不连贯、风格漂移的根因是没有共同记忆；共识让每章都带着全书的味道 |
| 连续性（continuity） | 前面发生的一切影响后面：人物、伏笔、关系、情绪 | 伏笔台账、人物卡进化、novel_knowledge、agent 日记/关系 | 巧思与伏笔、人物成长都靠连续性；没有它，每章都是孤立的 AI 生成片段 |

### 关键设计一：会议产物必须注入写作，不许「两张皮」

会议是会议、章节是章节，正是读者能读出 AI 味的原因——内容没有编辑部共识的沉淀。因此每类会议的产物不能只落报告：

- 会议产出「写作指令」（writing directives）：如「本卷巧思：第 3 章的握手动作在第 20 章回收」「守正确认：主角不知道自己是破绽」；落库后注入下一章生成的 writing_context。
- 会诊会（critique）的修改指令直接挂在对应章节/草稿上，写手重写时必读。
- 复盘会（retro）的经验经知识管家蒸馏进知识包，下一卷写作时按需调用。
- 选题会/收尾会的结论进入新书 bible 与完结状态，而不是只改蓝图数字。

### 关键设计二：议题池——编辑部「攒话题」的机制

真实编辑部不会随时开会，但茶水间里每天都在攒话题。系统已有雏形（topic_request 邮件），把它升级为正式的议题池：

- 任何 agent 在日常工作中都可以投议题（如守正发现设定隐患、阿读觉得某章会掉读、写手想聊下卷走向）；现有 outbox 已支持，只需在日记/消息注入时引导。
- 前端新增「议题池」视图：谁在什么时候投了什么，是否已被会议消费。
- 开 free 会或 topic 会时，议题池按热度/紧急度自动成为议程；会议结束，被消费的议题标记关闭，未被消费的保留。
- 攒够 N 条（可配置，默认 3~5）时，前端提示「编辑部有话想说，要开个会吗」——由你决定开不开，agent 不自行开会。

### 关键设计三：关系在会议中真实变化，并反向影响写作

现在 agent_relations 已有 trust/friction/familiarity，但会议中的互动还没有驱动它。补上后：

- 会诊会上守正尖锐打回 → 写手对守正的 friction 上升；写手按建议改好 → trust 上升。
- 提案被主编采纳 → 提案者 trust 上升；主编点名发言 → 双方 familiarity 上升。
- 关系变化注入写作上下文：写手知道守正会在设定上挑刺，写稿时主动自查；守正知道写手刚被阿读表扬过节奏，批评会更具体。这就是「编辑部压力」带来的真实质感。

### 关键设计四：读者视角进编辑部

阿读（reader）不只是一个打分器，应该像编辑部里的「读者代表」：

- 每章生成后，阿读写「读者视角笔记」：不是分数，而是「我在第几段想弃」「这里我会笑」「这句像 AI 写的，因为现实里没人这么说话」。
- 复盘会（retro）上，阿读带着一周的笔记和数据出席，编辑部把「完读率掉了 5 个点」翻译成具体问题（是钩子弱了，还是对话假了，还是节奏平了）。
- 读者笔记与质量门分开：质量门是硬底线（合规、字数、黑名单），读者笔记是软信号，进入写作指令但不直接拦稿。

## 四、改造方案（分步工程表）

### M1 · 会议类型模型（数据层 + 创建入口）

- `create_session(conn, topic, novel_id=0, kind="topic", ...)`：kind 白名单校验，落库；旧调用不传 kind 保持 'topic'，向后兼容。
- 新增 `MEETING_KINDS` 注册表（`novel_pipeline/config.py` 或 `tools/meeting_kinds.py`）：每个 kind 定义 `label`、`materials_keys`、`agenda_label`、`post_actions`、`default_attendees`。
- `meeting_sessions` 与 `weekly_meetings` 不改表结构（kind 字段已存在）；`weekly_meetings` 表名保留为归档表。
- 验收：迁移幂等；创建/查询任意 kind 成功；旧接口不带 kind 行为不变；新增测试。

### M2 · 材料注册表（按 kind 组装会议材料）

- 将 `architect_weekly.build_materials` 泛化为 `tools/meeting_materials.py`（或保留原函数名做 weekly 包装）：
  - `build_materials(conn, novel_id, kind, topic="")`；
  - 基础块：书信息 / 最近摘要 / 伏笔台账 / 蓝图 / 角色状态 / 质量 / 成本 / 热点 / 知识库 / 章节原文 / 失败运行 / 知识草稿 / 完结指标 / 议题池 / 读者视角笔记；
  - `MEETING_KINDS[kind].materials_keys` 决定组装哪些块；critique 额外拉章节原文与质量报告；retro 额外拉读者数据与读者视角笔记；incident 额外拉 `daily_runs` 失败记录与 audit；learning 额外拉 `knowledge_drafts`；review 额外拉 `character_evolution` 与完结指标；free 额外拉议题池。
- `architect_weekly.py` 保留为 `kind='weekly'` 的兼容入口（docstring 更新），`meeting_session` 改走新注册表。
- 验收：每种 kind 的材料字段断言；缺数据给默认值；`build_planning_materials` 复用同一套块。

### M3 · 议程模板与发言结构（prompt 层，字段兼容）

- `round_speech` 增加 `agenda` 参数：按 kind 注入「发言结构」与「开场指引」；JSON 字段名保持兼容（`weekly_summary` 保留为通用 `summary` 的别名输出，解析时 `summary = speech.get("summary") or speech.get("weekly_summary")`）。
- `chair_pick` 的 prompt 按 kind 注入会议性质说明（现在是硬编码「周会/新书选题会」两种）。
- `chair_summary` 报告增加 `kind`、`materials_summary`（用了哪些材料）、`agenda`（议程模板），保持旧字段不变。
- 缺段重试一次、发言失败占位跳过等兜底逻辑全部保留。
- 验收：weekly 输出与现有一致；incident/learning 发言含对应语义字段；缺段重试测试保持。

### M4 · 会后动作路由（按 kind 分派，幂等）

- 新增 `tools/meeting_actions.py`：`run_post_actions(conn, session_id, weekly_id, novel_id, kind, report, transcript, attendees)`。
  - `weekly`/`topic`：现有 apply_report + post-meeting actions + 写作指令注入；
  - `critique`：修改指令挂到章节/草稿 + 打回结论 + actions；
  - `retro`：经验草稿（distill_lessons）+ 写作指令更新（节奏/钩子/对话方向）；
  - `planning`：create_planning_from_next_book + actions；
  - `incident`：生成整改 action items + 调用 `distill_lessons` 落经验草稿（不自动采纳）；
  - `review`：产出完结/继续建议（落报告 + action items，不直接停更，停更仍人工确认）；
  - `learning`：产出知识包更新草案（knowledge_drafts，不自动采纳）；
  - `free`：仅行动项 + 记忆 + 灵感入点子池（轻量表或并入记忆）。
- 每个动作幂等（以 session_id 去重，重复执行不产生第二条）；失败 audit 留痕不阻塞会议完成。
- 验收：各类动作的 mock 测试；重复执行幂等断言；audit 有 `post_action` 记录。

### M5 · 写作指令与议题池（编辑部生活底座）

- 新表/字段：`meeting_directives`（meeting_id、kind、novel_id、directive、status，供写手注入）或复用 `agent_actions`；议题池直接用 `agent_messages(kind='topic_request')` 升级视图（新增 consumed_at 字段或关联 meeting）。
- 日更调度器在生成 writing_context 时注入：本卷/本周「编辑部共识与写作指令」+ 未回收伏笔 + 读者视角笔记摘要。
- 前端新增「议题池」区块：列出未消费议题、提案人、时间、关联会议；会议消费后标记。
- 验收：指令注入 writing_context 的断言；议题消费幂等；前端议题池渲染测试。

### M6 · 触发层与前端

- 触发层本期先做「手动创建时可选 kind」；事件驱动（日更失败自动开 incident 会、完结指标接近自动开 review 会）做成开关，默认状态由你确认（见第七节）。
- 前端 MeetingLive：创建会议增加 kind 选择（例会/专题/选题/会诊/复盘/评审/危机/学习/闲聊），按 kind 显示议程说明与默认参会人；直播头部显示 kind 徽标与议程。
- MeetingsPage：档案按 kind 筛选；报告详情展示「会后产出」区块（写作指令/蓝图数/新书/行动项/知识草稿/打回结论）。
- `control.py`：`run_weekly` 保留兼容，新增 `run_meeting(kind=..., topic=...)` 的通用 action（可选，本期先不动 control，避免扩大改动面）。
- 验收：前端 15 项测试不回归 + 新增 kind 选择与筛选测试；手动跑一次 incident 型 dry-run 会议。

### M7 · 回归、审查与文档

- 全量回归：`python run_tests.py`（371 后端基线）+ `cd webapp && npm test && npm run build`（15 前端基线）。
- 产出 `docs/reviews/YYYYMMDD-meeting-generalization-review.md`（P0–P3 + 影响评估表）。
- 更新 README / evolution.md：会议系统从「周会」章节改为「会议协作平台」章节；不暴露个人信息。
- 提交推送。

## 五、成本与风险

| 项目 | 评估 |
| --- | --- |
| LLM 调用成本 | 不新增调用次数；材料按 kind 裁剪反而省 token（incident 不需要 8 章摘要+热点，learning 不需要发布数据） |
| 回归风险 | 动的是核心会议引擎与日更注入，需 371+15 全量回归；weekly 行为作为兼容基线必须完全一致 |
| 输出稳定性 | 发言模板按 kind 变化可能偶发缺段，保留「缺段重试一次 + 占位跳过」兜底；JSON 字段兼容别名 |
| 数据迁移 | 无表结构变更，`weekly_meetings`/`meeting_sessions` 原样保留，零迁移风险 |
| 后端兼容 | `architect_weekly.py` 保留为 weekly 入口，`run_weekly` control action 不变，旧接口全部可用 |
| 前端改动面 | MeetingLive + MeetingsPage 两页，组件拆分已做过一轮，改动可控 |
| 关系/写作注入 | 关系事件钩子与 writing_context 注入需要动日更调度器，是本期最大的侵入点，用小步 + 开关控制 |

## 六、不做的事（本期明确排除）

- 不改表名、不做数据迁移、不退役 `weekly_meetings` 归档表。
- 不做 agent 自行开会的完全自治（会议始终由你发起；议题池只提示、不自动开会）。
- 不改动知识管家、完结机制的既有行为；review 会议只产出建议，不直接停更。
