# N12 图形面板立项清单（Phase 0 · 完整流程）

- 建立：2026-08-22
- 定位：U27 图形面板（三扇窗）的完整立项；按终极开发 skill Phase 0 四步（价值 → 目标 → 功能 → 可执行单元）定义，经用户确认后进入选技术栈。
- 前置：N24 API 服务层已收口（面板数据源）；N10 跨作品聚合、N19 事件流等可见性机制已就绪。

## 第 1 层：核心价值（01a）

### 一句话价值主张

为独自管理一部或多部作品的作者，解决「只能靠 CLI 逐条敲才能知道编辑部在干什么」的问题，带来「打开面板一眼看见动静、随时穿透到任意一层、该拍板就地拍板」的结果。

### 核心用户与核心场景

- 作者本人（同时开多部作品）：早上打开面板 → 看见哪部作品有新事件、哪里在等我拍板 → 点开作品穿透到写手记忆包 / 审稿意见 / 版本对比 → 就地拍板。
- 开源外部作者（次）：按 README 一条命令起面板，30 分钟内看到示例编辑部在动。

### 价值边界（明确不解决）

- 不解决写作本身：面板只做观察 + 穿透 + 拍板入口，创作与讨论仍在 CLI / API / 对话。
- 不解决实时共编、自动发布、多用户鉴权、移动端。
- 不把面板变成「第二个编辑器」或报表中心。

### 反盲从三问

1. 需求还是方案？「作者要直观看见编辑部动静并能拍板」是需求；Web 面板、三扇窗布局、轮询/SSE 是方案。
2. 依据是什么？回溯 G1（老板可穿透、关键处拍板）与 F17/F18/F19（实时观察流 / 穿透查看 / 关键节点提醒）；面板是这些可见性机制的图形呈现，不是新功能堆叠。
3. 不做会怎样？作者继续靠 CLI 猜状态，多作品时可见性成本升高；核心创作不受影响，但「老板视角」不完整。

## 第 2 层：核心目标（01b）

| 编号 | 目标 | 优先级 | 成功标准 | 验收方式 |
| --- | --- | --- | --- | --- |
| P-G1 | 三扇窗一屏可达：事件流 / 穿透查询 / 拍板提醒 | 必须 | 不切回 CLI，作者可在面板完成「看事件 → 打开作品 → 穿透任一层 → 处理待拍板」完整闭环 | 端到端演示 + 集成测试 |
| P-G2 | 数据同源：面板只消费 N24 API，与 CLI 同一时刻结果一致 | 必须 | 面板展示值与 CLI 对照一致；不复制业务逻辑 | 对照测试（同一数据双通道断言） |
| P-G3 | 开箱即用：一条命令起面板，本地 localhost 运行 | 应该 | 干净环境按 README 可复现；无 key 也可看示例编辑部 | fresh setup 演示 |
| P-G4 | 视觉可信：状态可扫、三态完整 | 可以 | loading / empty / error 三态齐备；可访问性与响应式达标 | 前端设计审查（pre-flight 清单） |

## 第 3 层：功能细化（01c）

| 编号 | 用户故事 | 优先级 | 所属目标 | 依赖 |
| --- | --- | --- | --- | --- |
| F-P1 | 作为作者，我想在面板看到最新事件流（谁在发言、谁写了、谁退了谁的稿），以便掌握编辑部动静 | P0 | P-G1 / P-G2 | N24 API（/events 已有；MVP 轮询） |
| F-P2 | 作为作者，我想一屏看到所有作品状态与待拍板清单，以便知道哪里需要我 | P0 | P-G1 / P-G2 | N24 API 补口：decision pending |
| F-P3 | 作为作者，我想从任一作品穿透查看草稿 / 版本 / 意见 / 记忆包 / 设定 / 检索，以便理解伙伴为什么这么判断 | P0 | P-G1 / P-G2 | N24 API 补口：inspect / draft / review / log |
| F-P4 | 作为作者，我想在面板直接 accept / reject / note，以便不必切回 CLI | P0 | P-G1 | N24 API 补口：decision 写操作 |
| F-P5 | 作为作者，我想事件流实时推送而不是手动刷新 | P2 | P-G1 | SSE 后置；MVP 用轮询 |

### 做 / 不做

**做**：F-P1～F-P4（MVP）、面板三态与可访问性、README 快速开始。

**不做**：面板写作 / 编辑界面、对话发送、实时共编、自动发布、多用户鉴权、移动端 App、重型图表可视化、SSE 实时推送（后置 F-P5）、模板管理界面。

### 依赖与实施顺序

API 补口（决策读写 / 穿透查询）是前端一切数据的前提 → 前端骨架 → 三扇窗 MVP → 拍板接线 → 设计打磨与 QA。

### 里程碑

- M9-面板-MVP：U27-A + U27-B + U27-C（最小可验证：三扇窗看得见）；U27-D 补闭环；U27-E 收质量门。

## 全局约束与风险

- 约束：本地单机、个人 + 开源使用；Python 生态为主，前端选型不得破坏「项目与 AI 适配」。
- 风险 1：引入 Node 工具链（若选 React/Vite）→ 维护与构建成本；应对：构建命令显式化、锁定版本、CI 接入。
- 风险 2：API 写面扩展（拍板）可能破坏只读优先纪律 → 应对：写操作收敛为决策三动作，其余全部只读。
- 风险 3：面板与 CLI 双通道结果漂移 → 应对：数据同源红线 + 对照测试。
- 决策记录：面板是「窗户」不是产品本体；创作与协作核心仍在 CLI / API / 对话层。
