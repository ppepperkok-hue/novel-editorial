## Findings

### [P1] 运行锁路径分裂：`control.py` 用 `ROOT/n8n_tmp`，而 `config.TMP_DIR` 是 `RUNTIME_ROOT/n8n_tmp`，桌面模式下互斥失效且周会锁会静默失败

**位置**：`novel_editorial/services/control.py:242-243`

**证据**：
- `novel_editorial/config.py:21` 定义 `TMP_DIR = RUNTIME_ROOT / "n8n_tmp"`（`RUNTIME_ROOT` 随 `NOVEL_DATA_DIR` 变化）。
- `control.py:242` 却写死 `lock_path = ROOT / "n8n_tmp" / "weekly.lock"`；依赖接口 `tools/workday.py:194/293/340`、`tools/editorial_daily.py:562` 同样用 `ROOT / "n8n_tmp" / "{db}.lock"`，而 `tools/publish_stock.py:378`、`tools/preflight.py:276` 用 `config.TMP_DIR / "{db}.lock"`。
- `desktop/main.js:111` 在桌面部署时设置 `NOVEL_DATA_DIR=userData`，注释明确 "the install dir stays read-only"、locks 应放 userData——但上述锁路径违反该约定。
- 实测复现：同一 db，`ROOT/n8n_tmp/demo.lock` 与 `RUNTIME_ROOT/n8n_tmp/demo.lock` 同时 `acquire_lock` 成功（`acquired=True` × 2）。

**影响**：
1. **并发保护失效**：桌面模式下日更链（workday/editorial_daily，锁在安装目录）与发布链（publish_stock，锁在 userData）互不互斥。`preflight.acquire_lock` 的 docstring 明确说这把锁存在的意义是 "prevent concurrent scheduled + manual runs from both passing preflight and double-publishing"。锁分裂后，scheduled task（`editorial_daily.py`，锁 A）运行期间手动触发发布（锁 B）可并发执行 → 重复发布。
2. **周会静默失败（假绿灯）**：安装目录只读时，`acquire_lock` 内 `lock.parent.mkdir(...)`（`tools/preflight.py:144`）抛 `OSError` 未被捕获；`_weekly_worker`（`control.py:237`）及其上层 `_spawn` worker（`control.py:230-234`）无任何异常处理 → 后台线程崩溃，`run_workflow_now` 已先返回 `{"ok": True, "started": True}`，无 alert、无 audit。用户看到"周会已启动"，实际什么都没发生。

**建议**：统一改用 `config.TMP_DIR`（与 `publish_stock`/`preflight` 一致），并给 `_spawn` 的 worker 加异常兜底 + `_alert`。

### [P2] `config.DB_PATH` 固定在 `ROOT`，不随 `NOVEL_DATA_DIR` 迁移，与同文件其余可写路径契约不一致

**位置**：`novel_editorial/config.py:31`

**证据**：
- 同文件 `TMP_DIR`(21)、`EXPORTS_DIR`(22)、`DATA_DIR`(23)、`ALERTS_LOG`(28)、`HOT_TOPICS_JSON`(29) 全部基于 `RUNTIME_ROOT`，唯独 `DB_PATH = ROOT / "demo.db"`(31) 固定安装目录。
- `desktop/main.js:67` 通过显式 `--db userData/demo.db` 掩盖了该问题；但 `web_api.py:1294` 的 `--db` 默认值、`desktop.py:34` 的默认值、`publisher.py:52` 的 `db.connect(config.DB_PATH)` 回退路径仍指向安装目录。
- 后果：`NOVEL_DATA_DIR` 模式下不经桌面壳直跑 `python -m novel_editorial.web_api`（无 `--db`）时，数据库写在安装目录（只读时写库失败/崩溃），且 DB 与 alerts/hot_topics/exports 分离在两个根目录，出现"面板看不到数据"的错位。

### [P3] free 模式死会话无运行中恢复：`get_active_session` 跳过 free 心跳检查，清理只发生在进程启动时

**位置**：`novel_editorial/services/meeting_session.py:134`

**证据**：
- `meeting_session.py:134`：`if heartbeat < cutoff and str(session.get("mode") or "rounds") != "free":` —— free 会话的心跳过期不会在运行中被标记。
- `web_api.py:1278` `_fail_orphan_sessions` 只在 `main()` 启动时执行一次；`tools/meeting_free_loop.py` 的 `_process_cold` 无异常包裹（`_run_candidates` 抛出如 LLM `RuntimeError` 时 worker 线程死亡）。
- 影响：free 会话 worker 崩溃后，会话永久保持 `running`，`create_session` 持续返回"已有会议进行中"，拒绝新会议，直到进程重启且心跳过期。

### 已核实但未列为 finding 的事项

- `generate_post_meeting_actions(dry_run=True)` 仍写 `agent_actions`：实测复现 1 行写入。但 `tools/agent_meeting.py:753-769` 已对 CLI dry-run 做门控（不调用该函数），且 `tests/test_activity.py:86-112` 明确断言 dry_run=True 写库——属测试锁定行为，无生产触发路径，不报。
- `web_api.py` 的 PANEL_TOKEN 检查可被伪造 `Origin` 头绕过：模块注释明确声明该信任模型（"A forged local Origin header is out of scope for a localhost trust model"），属文档化设计决策。
- GET/POST 未知路径返回 HTML 404（`send_error`）与其余 JSON 响应不一致：前端不依赖，仅为风格问题，不报。

## Conclusion

切片内语法、导入、DB 基础操作与 13 个 API 端点冒烟全部通过，主路径（开发模式）行为正常。但存在一个 P1 级缺陷：运行锁路径与 `config.TMP_DIR` 契约不一致，在桌面部署（项目的主要交付形态）下会导致发布互斥失效与周会静默失败。这是需要在下个周期修复的真实问题；F2/F3 为低风险一致性/恢复缺口。整体判定：**patch is incorrect**（存在需修复的 P1 阻塞项）。
