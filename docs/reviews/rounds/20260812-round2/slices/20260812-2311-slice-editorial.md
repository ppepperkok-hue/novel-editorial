Slice syntax and tests are clean (compileall OK; 354 targeted tests pass; dry-run daily chain completes), and most findings are deployment-scoped edge cases, but the ROOT-vs-RUNTIME_ROOT runtime-write defect (P1) deterministically breaks the scheduler and workday in the documented desktop deployment (read-only install dir, NOVEL_DATA_DIR set), which is a blocking issue under the project's own runtime contract.

Full review comments:

- Use RUNTIME_ROOT/TMP_DIR for run locks and runtime outputs — E:\code\novel-editorial\tools\editorial_daily.py:561-568
  All run locks and runtime artifacts are hardcoded to the install dir: `tools/editorial_daily.py:562` (`lock_path = ROOT / "n8n_tmp" / ...`), `tools/workday.py:194/293/340`, plus `bible.json` (`editorial_daily.py:1632`) and `daily_result.json` (`editorial_daily.py:1697`), while `config.TMP_DIR = RUNTIME_ROOT / "n8n_tmp"` (config.py:9-11) is never used. This contradicts the documented runtime layout: `desktop/main.js:76-90` states runtime artifacts (including locks) "live next to the DB in userData; the install dir stays read-only" and probes `userData/n8n_tmp`, and `desktop/main.js:111` sets `NOVEL_DATA_DIR`. In the packaged NSIS desktop deployment (read-only install dir), `preflight.acquire_lock`'s `os.open(O_CREAT|O_EXCL)` raises PermissionError inside `_preflight` (called from `services/control.py:157`), so every scheduled/manual daily run and every `workday.open/close/resume` fails; even when writable, lock/artifact files land in the install dir instead of the per-user data dir.

- Read reader stats and hot topics from RUNTIME_ROOT, not ROOT — E:\code\novel-editorial\tools\architect_weekly.py:16-19
  `architect_weekly.load_reader_stats` reads `ROOT / "demo_data" / "reader_stats.csv"` (architect_weekly.py:17) and `load_hot_topics` reads `ROOT / "hot_topics.json"` (line 37), but the writers use RUNTIME_ROOT-based paths: `tools/collect_reader_stats.py:23/185` writes `config.READER_CSV = RUNTIME_ROOT/demo_data/reader_stats.csv` (config.py:10-11, 27) and hot topics land under `config.HOT_TOPICS_JSON`. Under the desktop app (`NOVEL_DATA_DIR` set, desktop/main.js:111) these diverge, so weekly/planning meetings silently consume the bundled seed sample instead of live stats. Reproduced: with `NOVEL_DATA_DIR` pointing at a temp dir whose `reader_stats.csv` contains `finish_rate=0.99`, `architect_weekly.load_reader_stats()` returned the repo file's value `0.42`.

- Read the daily_runs row inside the lock in close/resume — E:\code\novel-editorial\tools\workday.py:330-341
  `workday.close` (workday.py:330-341) and `workday.resume` (workday.py:285-297) both fetch the `daily_runs` row *before* acquiring the run lock. If a user clicks resume and then close while the resume is in flight, resume re-produces and updates `published`/`status`, then close proceeds with the stale pre-resume snapshot: `_close_locked` reports `published = int(row["published"] or 0)` and computes `final_status` from the stale `row["status"]`, so a completed workday can be recorded/reported as `failed`/`partial` with an undercounted chapter count, and the stale data is what gets returned and written to the audit trail. Re-reading the row after acquiring the lock fixes it.

- Don't settle rework as done when REVIEW_RETRY_MAX is 0 — E:\code\novel-editorial\tools\editorial_daily.py:1070-1074
  In `_review_retry` (editorial_daily.py:1070-1074), `max_retries <= 0` immediately returns the original gate unchanged. The rework path in `_run_track` (editorial_daily.py:1287-1298) then calls `_settle_rework(conn, track_req, ok=bool(gate.get("passed")))`, so with `REVIEW_RETRY_MAX=0` (config default is 1, but 0 is a supported value) a colleague's rework request is silently ignored, the action is marked `done` with "即时重写已完成" and the message resolved as rework, while the chapter ships under the stale pass — the exact outcome R11-A2-01 was written to prevent. Return a forced-failed gate (or skip settling as done) whenever no retry round actually ran.
