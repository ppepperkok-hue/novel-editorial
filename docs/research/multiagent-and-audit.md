# 全链路审查与多 Agent 升级（2026-08-10）

## 一、审查结论（按严重度）

### 高危

1. **n8n 监听 0.0.0.0:5678**：管理界面暴露到所有网卡，局域网内可访问。
   已修复：`~/.n8n/.env` 增加 `N8N_LISTEN_ADDRESS=127.0.0.1`，重启后仅监听本机。
2. **单分支失败会中止整次执行**：A 章质量门/发布失败时抛错，n8n 默认停止，
   B 章可能已发布但「合并/汇总/记录」不执行，数据库缺 B 章，次日章节号错乱。
   已修复：
   - 质量门/校验发布/解析草稿改为「失败标记 + 短路」，不再抛错；
   - 新建草稿/保存内容/提交发布等网络节点 `onError: continueRegularOutput`；
   - 排版在无正文时 `return []` 短路该分支，另一章照常发布；
   - 汇总节点用 `safe()` 容错缺失分支，失败原因写入 `chapters[].error`。
3. **数据库无自动备份**：backup.py 存在但从未被调用。
   已修复：每日触发后新增「备份数据库」节点（保留最近 3 份）。

### 中危

4. **LLM JSON 输出脆弱**：解析大纲/解析作品资料直接 `JSON.parse`，偶发非法 JSON
   会导致全流程失败。已改为容错解析（去 fence + 提取 `{}` + 明确报错）。
5. **热点数据没接进日更**：hot_topics.json 已抓取但 Planner 看不到。
   已修复：get_meta.py 输出热点摘要，记忆包注入「近期热点」。
6. **A/B 章发布缺少幂等护栏**：手动重复执行会重复建草稿/发布（番茄每日字数上限
   是最后兜底）。已记录为已知限制，建议依赖 chapter_number 与数据库比对，留待后续。
7. **校验发布只认 `code===0`**：未核对「审核中/已发布」最终状态。
   已记录：后续可在发布次日用 `chapter_list` 复核。

### 低危 / 已知限制

- 番茄 Cookie 失效靠监控面板告警，无自动阻断；失效后需手动重抓。
- 完读率依赖手工导出的 `demo_data/reader_stats.csv`，无自动采集。
- n8n 管理员密码建议设为强密码（README 已提示）。
- 成本熔断未接入：DeepSeek 用量低（flash 为主），暂以月预算人工盯控。

## 二、多 Agent 策略（本轮落地）

参考 oh-story 的七 Agent 体系与 sumeru 的分模块编排，按「月预算 100 元、
每天两章」的约束，把流水线升级为多角色协作，全部复用 DeepSeek 已有 key：

### 现有角色（继续保留）

| Agent | 节点 | 职责 |
| --- | --- | --- |
| 策划官 | Planner出大纲 | 生成/增量更新故事圣经与两章细纲 |
| 世界观守护 | 守护细纲 → 解析守护（新） | 对照圣经检查细纲 OOC/吃书/伏笔/时间线，输出必须遵守的 constraints |
| 叙事写手 | 写手A/B | 按细纲 + 角色卡 + constraints 写正文 |
| 文字编辑 | 润色A/B | 去 AI 味、标点、节奏 |
| 逻辑审稿 | 审稿A/B | 六类底线问题 + 风格检查 |
| 读者体验审稿 | 读者审稿A/B（新） | 以普通读者口味评分：追读欲/钩子/情绪满足 |
| 主编终审 | 主编终审A/B（新） | 仲裁逻辑审稿与读者审稿冲突，输出最终 verdict 与 must_fix |
| 记忆官 | 提炼剧情A/B → 整理剧情A/B | 每章提取摘要、角色状态、事件、伏笔台账 |
| 架构师 | 架构师周会（独立工作流，每周日） | 输出未来蓝图增量、读者画像、卷目标微调，落库供日更使用 |

### 新增协作机制

1. **守护 Agent 不直接改稿，只输出约束**：`constraints` 注入写手提示词，
   失败时降级为空约束，不阻断日更（`onError: continueRegularOutput`）。
2. **双审稿串联**：逻辑审稿（能看不能读）→ 读者审稿（能读不能挑逻辑），
   质量门要求两者同时通过：`review.passed && reader.would_read_next &&
   reader.score>=7 && reader.hook_rating>=7`；读者审稿缺失时降级放行并记录。
3. **热点注入**：Planner/写手共享记忆包里新增「近期热点」，趋势元素可织入当前章。

### 每日新增成本

守护 1 次 flash + 读者审稿 2 次 flash，约每天 3 次轻量调用，
按 DeepSeek flash 计价估算每天不足 0.1 元，远在预算内。

## 四、第二轮加固（全部已知限制收口）

1. **Cookie 失效自动阻断**：新增 `tools/preflight.py`，每天运行前实测 book_list；
   失效/预算超限/当日已运行都会写 alerts.log 并让工作流跳到「结束」，不再白烧 LLM。
2. **幂等护栏**：preflight 检查当日是否已有 published 章节，防手动重复触发。
3. **完读率/追读率自动采集**：发现番茄作者后台真实接口
   `GET /api/author/stats/chapter_list_v1/v0/`（字段 read_completion_rate /
   follow_read_rate），新增 `tools/collect_reader_stats.py`，每天运行后写入
   `demo_data/reader_stats.csv`，前端自动展示。
4. **发布复核**：发布后调用 `/api/author/chapter/chapter_list/v1` 核对 item_id
   与 article_status，状态落库为 published / pending，不再盲信 code===0。
5. **成本熔断与台账**：新增 cost_logs 表，汇总节点收集所有 LLM 节点的 usage
   token 写入成本台账（单价可经 COST_PRO_PER_1K / COST_FLASH_PER_1K 环境变量
   调整）；preflight 按月预算 100 元熔断；前端新增「本月成本」卡片。
6. **n8n 管理员密码强化**：重置为 18 位随机强密码（已单独告知），建议登录后在
   Settings → Security 再改一次。

已知限制闭环后，剩余唯一手工步骤是 Cookie 过期后从作者后台重抓一次。

## 五、第三轮：多 Agent 协作深化

1. **主编终审仲裁**：逻辑审稿（能挑逻辑）与读者审稿（能挑体验）意见冲突时，
   由主编终审裁决：逻辑底线问题优先，读者意见写入 must_fix；质量门以
   `verdict === 'pass'` 为准，终审缺失时按双审结果降级。
2. **A→B 章串行承接**：写手B 现在消费 A 章结尾原文 + A 章提炼（summary/next_hook），
   要求开篇自然承接并回应悬念；审稿B 同样拿到 A 章结尾做衔接核对。
3. **守护输出角色言行要点**：守护细纲新增 `character_beats`（每角色说话要点/
   行为底线/当前状态），写手A/B 直接消费，人设从"静态卡"升级为"本轮指令"。
4. **角色卡永远带最新状态**：get_meta 把 characters 表的最新 state 合并进
   bible 角色卡，写手拿到的永远是"更新到上一章"的状态。
5. **架构师周会**（工作流 `架构师周会`，周日 08:10）：读圣经/最近摘要/伏笔台账/
   完读率/热点，输出未来蓝图增量、读者画像、卷目标微调，落库后日更 Planner
   的"可用蓝图"自动消费。

验证：55 节点深度校验通过；主编终审在"逻辑过/读者不过"场景正确判 revise 并
把钩子问题写入 must_fix；架构师读写闭环测试通过；仓库测试 45/46（monitor 老问题）。
