## 三、发现（Findings）

### [P1] apply_schedule 跨盘 fallback 与 ps1 的 `Join-Path` 不兼容，注册出指向不存在路径的计划任务（静默失败 / fake green）

**位置**：`novel_editorial/services/control.py:280-284`（本次新增的 `try/except ValueError: pass`）；契约文件 `scripts/install_daily_task.ps1:28`。

**证据（本机实测，Windows PowerShell 5.1）**：

```
PS> Join-Path "E:\code\novel-editorial" "C:\Users\someone\AppData\Roaming\novel-editorial\demo.db"
E:\code\novel-editorial\C:\Users\someone\AppData\Roaming\novel-editorial\demo.db   ← 垃圾路径，不存在
```

**完整触发链**（每一环都核对过）：
1. `desktop/main.js:54,68` 用 `app.getPath("userData")`（默认在 C: 盘）拼 DB 路径并 `--db` 启动 web_api；
2. `web_api.main()` → `control.set_db_path(绝对路径)`（`web_api.py:1176-1177`）；
3. 用户在面板保存定时 → `apply_schedule` → `_db_path()` 返回 C: 盘绝对路径 → `os.path.relpath(..., ROOT=E:\...)` 抛 `ValueError` → `except: pass` 保留绝对路径；
4. ps1 收到 `-DbPath "C:\...\demo.db"` 后无条件 `Join-Path $projectDir $DbPath` → 拼成 `E:\code\novel-editorial\C:\...\demo.db`；
5. 计划任务注册成功（`Register-ScheduledTask` 不校验路径），每天执行 `tools/editorial_daily.py --db <垃圾路径>` —— sqlite 会在垃圾路径**新建空库**，实测运行结果：`"error": "当前没有可发布的连载作品，请先开新书会并完成建书"`，exit 1，输出被 schtasks 吞掉。

**为什么是本次提交引入的回归**：改动前 `relpath` 直接抛 `ValueError` → web_api 返回 500（响亮失败，用户看得到）。改动后面板返回 `ok=True`「已注册计划任务」，实际任务每天静默空跑——本次提交把显式报错换成了静默失效，正是 commit message 声称要修好的「cross-drive relpath fallback」场景。本仓库在 E: 盘、桌面 userData 在 C: 盘，恰好就是默认部署形态。

**修复方向**：ps1 先判 `[System.IO.Path]::IsPathRooted($DbPath)`，rooted 时跳过 `Join-Path`，否则保持现状；或 control.py 恒传绝对路径并让 ps1 只做 rooted 判断。

### [P3] run_session 新 fallback 仍在默认库查行内 db_path，跨库会话依旧静默漏跑，与新增注释自相矛盾

**位置**：`novel_editorial/services/meeting_session.py:330-339`。

**证据（实测复现）**：会话创建在 `other.db`，`config.DB_PATH` 指向 `default.db`，调用 `run_session(1, db_path="")` → 无异常返回，`other.db` 里该会话 status 仍是 `running`。原因：`db.connect(config.DB_PATH)` 后在新代码里查 `meeting_sessions` 的 `db_path`，行不在默认库 → `row_db=""` → 继续在默认库跑 `_run_locked` → `row is None` 静默 return（`meeting_session.py:350-352`），会话永远卡在 running，无日志无告警。新注释宣称「never silently fall back to a hardcoded demo.db lookup that silently misses sessions in other DBs」，但实现仍以 `config.DB_PATH` 为查找起点，跨库会话照旧被漏。

当前调用图（`start_session_async` 总是把同一 db_path 同时传给建行和 `run_session`）下此分支不可达，属于潜在缺陷；但代码注释与实现不符，将来任何以空 db_path 恢复会话的入口都会踩中。修复方向：查找前无法定位行内库时显式报错/置 failed，而不是静默继续。
