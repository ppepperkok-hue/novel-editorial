# 修复环节的 CLI 并行化：划分方案与评估 · 2026-08-12

## 一、目标

审查已六路并行（`run_review.ps1 -Scope slices`）。修复目前由主 agent 串行逐批执行，耗时且视角单一。目标：修复也用 CLI 子 agent 并行，但**按文件不相交分组**，避免多 agent 改同一文件的冲突；主 agent 只做分组、派发、收口回归、提交、登记。

## 二、划分原则（按优先级）

1. **文件不相交**：同一文件的多个 bug 必须进同一组；不同组之间零文件重叠——这是并行安全的前提。
2. **依赖分层**：数据层/公共配置（db.py、config.py、llm_client.py、web_api 路由）改动影响面大，由主 agent 或单独一个 agent 串行先做；叶子模块（tools、webapp、scripts）可并行。
3. **按修复类型聚组**：同一批的 bug 类型尽量一致（纯健壮性容错、死代码清理、路径解析、前端 UI），agent 一次调用解决一批同质问题，上下文聚焦。
4. **规模上限**：每批 ≤8 个 bug 或 ≤5 个文件，超了就拆——小步让单 agent 输出可控、主 agent 收口可审。

## 三、分组流程（每轮审查后执行）

```
审查报告（slices-summary）
  → 主 agent 按文件归类 bug
  → 合并同文件/强关联文件 → 组
  → 依赖分层（公共层先，叶子层后/并行）
  → 每个组生成「修复任务包」：
       bug 清单（编号/位置/问题/期望）
       只许改的文件列表
       验收（跑相关单测 + 语法检查，不提交）
  → 并行派发 N 个 CLI（codex exec，flash）
  → 主 agent 收口：全量回归 → 抽查关键修复 → 提交 → 登记修复表
```

## 五、评估

| 维度 | 评估 |
| --- | --- |
| 可行性 | 高：CLI exec 已验证可用；文件不相交分组的并行无冲突；每组的 bug 清单来自审查报告，信息自包含 |
| 速度收益 | 中-高：N 组并行，总时长从「所有修复串行」降到「最慢组 + 主 agent 收口」；但收口（全量回归 80 秒 + 抽查 + 登记）仍是串行成本 |
| 视角收益 | 高：不同 agent 修不同模块，打破主 agent 的路径依赖，可能发现主 agent 修漏/修错的地方 |
| 成本 | 每组一个 CLI 进程（flash），与审查同量级；按组规模控制在合理 token 内 |
| 主要风险 1：修复质量参差 | 缓解：任务包明确到文件与期望；主 agent 收口时全量回归 + 抽查关键修复（尤其公共接口） |
| 主要风险 2：并行改工作树 | 缓解：文件不相交分组是硬约束；公共层（db/config/web_api 路由）不并行 |
| 主要风险 3：CLI 无交互、任务歧义 | 缓解：bug 清单写清「位置 + 现状 + 期望 + 验收命令」，宁细勿粗；修复 agent 只改指派文件，不做顺手优化 |
| 边界/底线 | 外部副作用（番茄发布/删除/建书）相关修复由主 agent 人工核对，不交给 CLI 实跑；数据层与公共接口改动由主 agent 决定是否串行；每批修复后全量回归是硬门槛 |
| 与现有流程衔接 | 修复记录、提交、报告归档仍由主 agent 统一执行，CLI 只产出代码改动；与「先汇总再归档」的审查纪律不冲突 |

## 六、结论

方案可行且收益明确：修复从「主 agent 串行」升级为「按文件不相交分组 + CLI 并行 + 主 agent 收口」。关键成功条件是三条硬约束：**文件不相交、任务包自包含、全量回归门槛**。建议下一轮（第三轮）审查后按此方案试点，先小规模（3 组）验证并行稳定性，再放开到 5 组。
