Full review comments:

- [P2] Same-second event_id collision silently drops free-meeting user messages — E:/code/novel-editorial/novel_editorial/services/meeting_session.py:168-176
  In `advance_session` free mode, `event_id` is `f"adv-{session_id}-{_now()}"` with second-resolution `_now()`. `meeting_free_loop.submit_event` dedups by `event_id` (verified: two distinct messages submitted within one second produce identical ids and the second returns `{'ok': True, 'duplicate': True}` and is never enqueued). `advance_session` discards `submit_event`'s return value, so the API still answers `{'ok': True}` and the frontend clears the input — the message is lost silently. The dedup also cannot catch real retries (each request generates a fresh id), so it only ever drops legitimate distinct messages. Fix: use a UUID or monotonic counter for `event_id` (and optionally surface `duplicate` in the API response).

- [P3] Idle free sessions are reaped as failed after the 60-min heartbeat timeout while their loop is still alive — E:/code/novel-editorial/novel_editorial/services/meeting_session.py:123-141
  Free sessions stay `status='running'` for their whole lifetime (they never park at `awaiting_input` like rounds mode), but the heartbeat is only refreshed when a user event arrives (`tools/meeting_free_loop.py` `_process_event`; `_process_cold`/`_speak` never update it). After ~60 minutes of inactivity, `get_active_session` (meeting_session.py:134-139) — or `_fail_orphan_sessions` on the next startup — marks the live free session `failed`; subsequent `advance_session` calls still return `{'ok': True}` while `_process_event` drops the events (status check), so the user's messages are silently discarded. Consider having the free loop tick the heartbeat while idle, or excluding `mode='free'` running sessions from the stale-reaping path.

- [P3] New meeting web endpoints have no test coverage — E:/code/novel-editorial/novel_editorial/web_api.py:307-374
  The three endpoints added in this slice — `GET /api/meetings/events` (SSE), `GET /api/meetings/messages`, and `POST /api/meetings/interactions/respond` — have zero coverage in `tests/test_web_api.py` (the 20 existing tests stop at `/api/meetings/cancel`). The SSE stream in particular is the only path that exercises `MeetingEventHub` subscribe/unsubscribe through HTTP. Add at least an endpoint-level test per route (the SSE one can publish an event and assert the `data:` frame).

- [P3] Meeting SSE endpoint lacks the connection cap and bound that `_sse` has — E:/code/novel-editorial/novel_editorial/web_api.py:307-335
  `_get_meeting_events` holds one `ThreadingHTTPServer` thread and one unbounded `queue.Queue` per subscriber for the life of the connection, with no equivalent of the `_MAX_SSE = 8` cap used by the snapshot `_sse` endpoint. `MeetingEventHub.publish` uses `put_nowait` with an unreachable `except queue.Full` (unbounded queues never fill), so a subscriber that stops reading (stalled network, suspended machine) accumulates events in memory indefinitely. For a localhost single-user tool this is low risk, but it is inconsistent with the existing SSE convention; capping subscribers and/or bounding the queue would close the gap.
