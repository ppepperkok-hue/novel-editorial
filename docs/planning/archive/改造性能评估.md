# 项目改造性能评估（2026-08-11）

## 结论

改造性能总体良好，三个结构性瓶颈需要留意：

- **好**：单入口调度器（`tools/editorial_daily.py: daily()` + `_agent()` 是唯一
  LLM 调用入口）、纯函数层（`tools/editorial_steps.py` 可独立测试）、SQLite 幂等
  迁移机制、279 后端测试 + 8 前端测试的 TDD 基建、工具式知识调用已跑通、
  会议系统有完整状态机可借鉴（`services/meeting_session.py`）。
- **瓶颈 1**：`tools/editorial_daily.py` 935 行单文件，`_Ctx` 贯穿全链。
  加能力（消息/记忆/关系注入）集中在 `_agent`/`build_system`/`_run_track` 三处，
  改动集中但需防回归。
- **瓶颈 2**：`novel_editorial/web_api.py` 968 行、25 个手写 `elif path` 分支。
  每加一个前端功能就要往巨型 handler 塞分支，是后续改造最易踩冲突的位置。
- **瓶颈 3**：前端组件偏大（DashboardPage 464 行），页面路由为手写 if 链；
  新增页面走 NAV/PAGE_META 模式成本低，暂不需要重构。

## 逐改造目标评估（对应初心接续路线）

### 1. 编辑部人格化（mailroom 消息 + 记忆/关系注入 + 两级完工）—— 下一任务

现状与改造量：

- 数据层：`agent_diaries`/`agent_states`/`agent_actions`/`agent_activity` 已存在；
  缺 `agent_messages`/`agent_relations`/`agent_memories` 三张表（db.py 无定义），
  需新建，幂等迁移机制现成。
- 注入点：`agent_tool_loop.build_system()` 是唯一 system 组装点；调度器
  `_agent()` 是唯一调用入口。收件箱/记忆/关系快照注入只需扩展这两处 + outbox
  统一落库，改造量小且集中。
- 两级完工：`daily()` 状态机已有 `completed/partial/failed`，扩展
  `completed_with_pending` 只改状态判定与 `_finish_run`，局部改动。
- 周记提炼：`write_diaries.weekly_payload()` 已聚合本周简报+日记+上周周记，
  `write()` 调用点加 `memory_updates`/`relation_updates` 字段即可。
- 成本：注入合并在现有 LLM 调用内，不新增调用次数，不改变预算结构。
- 风险：中低；`_agent` 成功/失败路径与 daily 四态已有测试锚点，TDD 可行。

### 2. 审稿打回重写（回环）

改动集中在 `_run_track`（写手/润色重跑 + 次数上限），`build_payload` 加
revision 字段；重试成本翻倍由既有预算熔断兜底。风险中低。

### 3. 完结机制（ending_judge 周检）

`ending_judge` prompt、`finish_remaining` 字段、`publish_stock` 完结停更逻辑
均已存在；接入点 = `run_weekly` 链 + 周会材料注入。风险低。

### 4. 统一留痕（audit_logs 全类别）

`audit_logs` 已存在，关键操作已写；缺 guard 拦截意见、会议逐条发言、运行
detail 结构化。增量补写点，机械改动。风险低。

### 5. 人物卡进化（character_evolution）

表与 `record_work` 写入已存在；缺周会固化与前端展示增强。改动小。

## 运行性能现状（顺带）

- 单次日更 LLM 调用约 15 次（A/B 双轨），失败最多 ×3 重试；成本按
  pro/flash 单价入账，月度熔断。
- 单次真实运行预计 20–60 分钟（LLM 主导）；锁 12h 陈旧回收覆盖。
- 面板轮询：dashboard 5s / control 15s / executions 30s / flow 15s；SSE 上限 8。
- SQLite WAL + daily_runs 索引；迁移幂等。
